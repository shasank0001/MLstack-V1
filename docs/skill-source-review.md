# Workflow source review

Reviewed 21–22 October 2026 for MLStack 0.3: a local Linux/PyTorch workbench using Pi, managed runs, structured metrics and durable research memory. This is a curation record for maintainers. It explains which ideas became local guidance, which require a future task, and which conflict with the application contract.

The review covered project definition and planning, coding and testing, data work, experiment design, debugging, evaluation, performance, reproduction, reporting and research continuity. Earlier findings were followed by a final pass across primary maintainer sources. Selection was based on a concrete decision the guidance could improve, its local fit and its operational assumptions. A repository's popularity or an attractive skill catalog was not sufficient.

No third-party instruction pack was installed globally, automatically enabled, or vendored wholesale. The bundled text is an original adaptation of selected methods, with source links retained in relevant references. Upstream branch links can change; review them again before importing new behavior. A reviewed source is evidence for a method or library behavior, not proof that adding instructions improves this agent's results.

## Bundle decision

Keep two concise entry points: `ml-project` for definition/planning and `ml-research` for investigation and research work. Use on-demand references and eleven `/ml` routes, rather than a separate skill or tool for each small action. The three ML tools and six coding tools retain their existing responsibilities. [The workflow guide](workflows.md) documents the interface and permissions.

Adapt a source only when it helps select the next observation, identify an evidence gap, constrain a comparison or make a useful deliverable. Ordinary subtraction, run inspection and cancellation need no extra playbook. Host-enforced discuss/plan/act rules remain authoritative over all guidance.

## How the decisions enter MLStack

`ml-project` uses the definition and planning ideas for a brief, success criteria, constraints, baseline and a bounded next step. `ml-research` routes to onboarding, data, experiment design, evidence-led debugging, evaluation, error analysis, sanity checks, performance, reproduction, reporting and continuity. Hugging Face and MLflow remain optional task-specific references.

The guidance preserves distinctions that tools alone cannot decide: whether a split leaks information, which boundary first failed, whether a comparison measured equal useful work, and whether a finding follows from the captured evidence. Existing tools still control execution, provenance, metrics and research history. A report should say when prediction artifacts, evaluation identities or repeated runs are missing; the agent must not fill those gaps with invented evidence.

External resources stay disabled except the reviewed bundle. There are no global installs, automatic uploads, cloud training defaults, extra tool wrappers, mandatory orchestration panels or added provider configuration. Computational diagnostics and data exploration remain subject to act mode and execution approval. A plan or skill cannot authorize a run.

## Evidence needed before claiming benefit

Source review establishes a reason to try the guidance. Structural validation establishes valid skill metadata, routes, linked references and an allowlisted resource surface. Runtime tests establish access behavior. Actual agent tasks establish observed use under a stated provider/model. None alone demonstrates a causal quality improvement.

A useful matched evaluation compares the same fixture and model with and without the relevant guidance. Candidate tasks include distinguishing a serialization failure from a training failure, detecting a false speedup caused by reduced work, preserving an inconclusive hypothesis, and checking an unfair evaluation identity. Review correctness, evidence support, unnecessary launches, refusal handling, and response length. Retain failures and quota interruptions; do not report an incomplete provider attempt as a passed workflow. More tasks and repeated trials are needed before a broad improvement claim.

The completed v0.3 nine-phase workflow passed its behavioral assertions. A separate matched read-only evaluation pair on the same free model found train/holdout preprocessing leakage and a simultaneous hyperparameter change in both conditions. Neither executed commands or edited files. The control used 584 words and 14 tool calls; the skill condition used 720 words and 16 calls and introduced unsupported directional/causal reasoning and an inconsistent follow-up proposal. This pair demonstrated no added benefit. It does not justify a general negative or positive effect claim, and no probe rerun is claimed after the resulting guidance refinement.

See [workflows and limits](workflows.md#validation-and-limits) and [the validation record](validation.md). The historical v0.2 live results predate this bundle and cannot establish its effectiveness.
